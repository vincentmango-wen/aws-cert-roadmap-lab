# SQS Standard と FIFO：メッセージの順序要件で選ぶ

## 選択のポイント

Amazon SQS で処理を待機させると決めたら、次に同じ業務対象への更新を順不同で処理できるかを考える。本記事はキューの選択に絞り、SQS 全般の紹介は繰り返さない。

- 順序を必要とせず、重複に対処できる独立した通知処理：Standard を選ぶ。
- 注文の作成後に支払いを確定する必要がある：FIFO を選び、注文 ID を `MessageGroupId` にする。
- FIFO の順序保証はメッセージグループ内であり、すべての注文にまたがる全体の順序ではない。

## 比較表

| 判断項目 | Standard | FIFO |
|---|---|---|
| 配信と順序 | 少なくとも 1 回の配信とベストエフォートの順序維持。重複や順序の入れ替わりがあり得る | 同じ MessageGroupId 内で保序。異なるグループは並行処理できる |
| 送信側の重複排除 | アプリケーションが重複に対処する | MessageDeduplicationId またはコンテンツベースの重複排除で、5 分間の重複排除期間内の重複送信を防ぐ |
| MessageGroupId | fair queues を有効にし、ノイジーネイバーによる他テナントの滞留時間への影響を軽減する。FIFO の順序保証はない | 各メッセージで必須。独立して順序を保つグループを識別する |
| スループットの判断 | 大量の独立した処理に適する | 並行度はグループの分布に左右される。リージョン、バッチ、高スループット設定に応じたクォータを確認する |
| コンシューマーの責任 | 重複と順序の入れ替わりに対処する | グループ内の順序を守り、業務上の副作用の重複も防ぐ |

## 試験ガイドと判断のポイント

SAA-C03 のシナリオで、疎結合化や急増トラフィックのバッファリングだけが要求されているなら、それだけで FIFO と判断しない。「同じ注文の状態遷移を逆転させない」などの順序要件を探し、グループキーを選ぶ。

FIFO の送信側重複排除は、決済やデータベース更新が一度だけ実行されることを保証しない。決済を終えたコンシューマーがメッセージを削除する前に失敗すれば、再試行時に完了済みの業務操作を識別する必要がある。重複排除と冪等性は異なる層の問題を扱う。

## 実務での使い分け

一つ目は独立した通知処理である。異なる注文の通知を全体の時刻順に送る必要がなく、コンシューマーがイベント ID で重複送信を防げるなら、Standard で要件を満たせる。

二つ目は注文の状態更新である。A1 は注文 A の作成、A2 はその支払いの確定を表し、B1・B2 は注文 B の同じ手順を表す。図は**同じグループ内の処理順序**を示し、2 回の `ReceiveMessage` 呼び出しを示すものではない。

```text
FIFO：同じグループ内の処理順序
MessageGroupId=order-A    A1 → A2    注文作成 → 支払い確定
MessageGroupId=order-B    B1 → B2    注文作成 → 支払い確定
異なるグループは並行処理可能。A と B の間に全体の順序保証はない。
```

AWS は同じグループの複数メッセージを 1 回の `ReceiveMessage` のバッチで返すことができ、グループ内の順序を維持する。コンシューマーもそのグループを順番に処理する必要がある。同じグループのメッセージは順番に処理し、A1 の処理が完了してから A2 を処理する。異なるグループは独立して処理できる。

再試行、可視性タイムアウト、冪等性の背景は [SNS・SQS・EventBridge の比較](/comparisons/sns-vs-sqs-vs-eventbridge)を参照。

## よくある誤解

- 「Standard も MessageGroupId を指定すれば保序する」：有効になるのはテナント間の公平性を保つ fair queues である。同じグループのメッセージも並行処理でき、FIFO にはならない。
- 「FIFO なら同じ業務イベントを二度処理しない」：5 分間の送信側重複排除とコンシューマーの業務上の冪等性は異なる。期間外の再送やコンシューマー障害後の再試行には、アプリケーション側の対策が必要である。
- 「すべてを同じグループにすれば最も安全」：独立して処理できる注文まで直列化される。共通の順序が本当に必要な業務対象ごとに分ける。
- 「一つのグループからは一度に一件しか受信できない」：同じグループでもバッチで返される。保序は一件ずつの受信を意味しない。

## まとめ

独立していて順序の入れ替わりを許容できる処理には Standard を検討する。同じ業務対象への更新に厳密な順序が必要なら、明確なグループキーを持つ FIFO を使う。どちらもコンシューマーの冪等処理が必要であり、fair queues は FIFO のグループ内順序保証の代わりにはならない。
