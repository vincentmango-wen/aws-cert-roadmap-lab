# Weekly production release (#376)

Routine releases start Sunday at **22:00 Asia/Taipei**. The approved dev-to-master merge and first S3 write gate must pass within that window (22:00 through 22:29:59); failure or delay does not shift the slot. The writer checks the claimed window again immediately before launching S3 sync, after AWS credential setup. A late credential response stops the release and leaves the weekly marker intact. The read-only scheduled run at 22:00 reports source changes; it never opens or merges a PR, requests AWS credentials, or deploys. A maintainer can prepare the PR ahead of time. Keep `dev` stable once the reviewed head is frozen. Use a standard merge commit, not squash/rebase. Arrange a separate author and approving/merging maintainer for this same-repository release; self-approval never counts. Frontend CI and path-applicable AIDD CI must succeed on the exact head before merging. Other required checks remain enforced by GitHub branch policy.

## Changeover (requires separate approval)

1. Confirm the existing Deploy Frontend workflow is disabled and drained. Leave #382 and the retired incremental prototype untouched. Keep the temporary S3 write guard in place. Capture prior workflow state and the exact last verified production artifact and recovery access. Do not cut over without a retrievable artifact or equivalent verified S3 version recovery and an independent recovery identity.
2. Review and merge this configuration PR while the existing workflow is confirmed disabled; no content release is part of this merge. Verify the exact merged workflow and its disabled state. Confirm that the trusted repository's master rules require PR review and all applicable checks, disallow routine bypass, and serialize merges in the release window. Protect the weekly claim tag namespace from routine updates/deletion while allowing the deployment workflow to create it.
3. Confirm the protected `aws-production` environment exists with a required reviewer, protected master-only deployment, and the appropriate no-bypass settings. Verify the AWS role trust accepts this environment's intended OIDC subject and no undesired writer. Adding an environment may change the OIDC subject: never widen AWS trust as a workaround. Confirm the AWS and GitHub settings with the owner. Fixing access, enabling the workflow, turning on `AWS_WEEKLY_RELEASE_ENABLED` and removing the temporary S3 guard are separately authorized cutover steps, not PR-review side effects.
4. Rehearse without writes: flags unset/false, no AWS authentication. Validate the empty, red, stale, outside-window and duplicate cases. Before release, pause unrelated merges to master while the artifact is publishing. Require a single active writer and recheck the protected environment, flag, exact master and last known artifact before opening the write gate.
5. When the owner explicitly authorizes a real release in the next eligible window, observe exactly one deploy run and one weekly claim tag, record S3 sync counts/bytes where available, then verify the homepage and representative routes in all three locales. No-change weeks are skip evidence, not live release acceptance. The successful static export archive is retained 14 days; retain the confirmed baseline separately before it expires.

## If a merge reaches master without a verified deployment

The Sunday report compares source only. An empty dev-to-master diff can coexist with a stale production site. Compare the merged SHA with the last confirmed deployed SHA, the workflow result and any weekly claim tag. Inspect the expected production paths only if needed to reconcile the outcome. Mark the release **unconfirmed** until the served version is verified; do not close #376 based on the source preview.

- **No AWS writes:** Keep the previous site serving. Record the missed release and retain the reviewed merge SHA. A new push, repeat merge, or deletion of the weekly marker is not a recovery plan. Escalate to the owner for an explicit decision: defer to the next legitimate release (which includes the already-merged source) or approve a one-off, independently reviewed recovery of the exact tested artifact. Do not fabricate a frontend change to trigger the writer.
- **Any AWS writes or uncertain write state:** Apply the rollback sequence below first. Treat republishing the merged revision as a separate approval after the previous known-good site is confirmed. Neither case uses a workflow rerun or bypasses normal permissions.

## Stop / rollback

- Before any S3 write: disable the writer, turn off the release flag and keep or reinstate the S3 write guard. Inspect running/queued jobs, verify no live writes, and do not re-enable the old workflow in parallel.
- After a failed or partial write: stop new releases, let the owner-approved recovery operator confirm all in-flight writes actually stopped, then restore the last verified artifact (including previously deleted assets) via the one approved recovery writer. Verify S3 and restore relevant CloudFront cache entries, then check representative public routes. A Git revert alone does not restore deployed files. If there is no verified baseline or recovery is incomplete, keep publishing disabled and escalate.
- Never remove the weekly claim tag to auto-retry; it marks a claimed attempt, not a successful deployment. Do not rerun a failed production workflow. A deliberate recovery outside the release window is a separately approved incident action.
