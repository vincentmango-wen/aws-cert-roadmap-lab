# AWS責任共有モデルを初心者向けに整理する

AWS Cloud Practitionerで最初に押さえるべき考え方が、責任共有モデルです。これは「AWSが全部守ってくれる」という話ではありません。AWSが守る範囲と、利用者が守る範囲を分けて理解するための考え方です。

## 結論

AWSはクラウド基盤そのものを守ります。利用者は、クラウド上でどう設定し、どう使うかを守ります。

ざっくり言うと、AWSは「クラウドのセキュリティ」に責任を持ち、利用者は「クラウド内のセキュリティ」に責任を持ちます。

## AWS側の責任

AWS側の責任は、物理的なデータセンター、ハードウェア、ネットワーク基盤、仮想化基盤などです。利用者がデータセンターに入ってサーバーを守ることはありません。その部分はAWSが管理します。

たとえば、物理サーバーの故障対応、データセンターの入退室管理、電源や空調の管理はAWS側の責任です。

## 利用者側の責任

利用者側の責任は、IAMユーザーやIAMロールの権限設定、S3バケットの公開設定、EC2のOS設定、アプリケーションの脆弱性対策、保存するデータの管理などです。

たとえば、S3バケットを誤ってパブリック公開した場合、それは基本的に利用者側の設定ミスです。AWSがS3というサービス基盤を安全に運用していても、利用者が公開設定を間違えれば情報漏えいにつながります。

## サービスによって責任範囲は変わる

責任共有モデルは、利用するサービスによって利用者側の責任範囲が変わります。

EC2はOSやミドルウェアの管理が利用者側に残ります。一方、LambdaやDynamoDBのようなマネージドサービスでは、サーバー管理の多くをAWSに任せられます。

ここが試験で問われやすいポイントです。サービスがマネージドになるほど、利用者はインフラ管理から離れ、データ、権限、設定、アプリケーションに集中します。

## 試験で問われるポイント

Cloud Practitionerでは、次のような観点が問われます。

- AWSはデータセンターや物理基盤を管理する
- 利用者はIAM、データ、アプリケーション設定を管理する
- EC2ではOSパッチなど利用者側の責任が大きい
- マネージドサービスではAWS側の管理範囲が広がる

## 実務での注意点

実務では「AWSだから安全」ではなく、「AWSを安全に設定できているか」が重要です。特にIAM、S3、セキュリティグループ、CloudWatch Logsは初学者が事故を起こしやすい部分です。

このサイトでも、S3は直接公開せずCloudFront OAC経由にし、GitHub ActionsのIAM権限もS3デプロイとCloudFront Invalidationに絞る設計にしています。
